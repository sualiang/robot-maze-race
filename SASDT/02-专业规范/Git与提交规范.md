# Git 与提交规范

> **版本**：V1.0 | **最后更新**：2026-07-25

---

## 分支策略

- **所有项目默认在 `main` 分支开发**
- 单仓库、单开发者、单环境部署场景下，分支管理无价值
- 只有明确需要多人协作或多阶段发布时，才创建 feature 分支
- 创建分支前必须获得总监或人类的批准

## 提交信息格式

使用 Conventional Commits 格式：

```
<type>: <简短描述>

<可选的详细说明>
```

| Type | 使用场景 |
|------|---------|
| `feat` | 新功能 |
| `fix` | Bug 修复 |
| `refactor` | 重构（不新增功能不修 Bug） |
| `docs` | 文档变更 |
| `test` | 测试相关 |
| `chore` | 构建/工具/依赖变更 |
| `perf` | 性能优化 |

## 提交流程

```
修改代码 → 自测通过 → git add → git commit → git push
```

**自测通过后再提交**，这是底线。

## 强制规则

| 规则 | 说明 |
|------|------|
| ❌ 不提交未验证的代码 | 至少通过编译和 lint |
| ❌ 不提交包含密钥的代码 | 提交前检查是否意外包含敏感信息 |
| ❌ 不提交大文件 | 避免提交 node_modules、dist 等目录 |
| ✅ 有意义的 commit message | "fix bug" 不够，要描述改了啥 |
| ✅ 小步提交 | 一个功能一个 commit，不攒一大波一起提 |
| ✅ 频繁推送 | 代码在本地越久越危险，及时推送 |
